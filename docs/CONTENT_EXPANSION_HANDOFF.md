## 2. 已確認的產品決策

### 2.1 首頁編輯提示

刪除 Hero 中目前可見文字：

> 首頁問題是編輯提問，不是成員名言。

位置目前在 `index.html` 的 `.hero__note`。

原因：

- 主標題沒有引號或成員署名，一般讀者不太會將它誤認為直接引言。
- 這句話會在故事剛開始時把注意力拉到編輯防禦說明。
- 與先前已移除的閱讀限制／圖片脈絡 UI 有相同的閱讀干擾問題。

不要只把它藏成小字、tooltip 或 Hero details。應從 Hero 可見內容移除。

### 2.2 第 13 章集中說明

在第 13 章「資料來源與可信度」的編輯方法附近加入一則簡潔規則，建議文案：

> 本站未加署名的章節標題、提問與反思句，均為編輯設計；只有明確標示說話者與來源的內容，才視為成員原話或媒體引述。

可微調語句，但必須清楚區分：

- 編輯標題／提問。
- 成員原話。
- 媒體引述或轉述。
- 可驗證事實。

這則說明只需集中出現一次，不要重新散布到每章。

### 2.3 內容增量

目標不是精確把字數乘以二，而是使第 2–12 章的正文總量增加約 70–100%。

優先增加：

1. 故事情境。
2. 可由來源支持的事件脈絡。
3. 可理解的產業／媒體識讀知識。
4. 回到青少年自身的問題或觀察。

不得增加：

- 沒有來源的新傳記事實。
- 猜測性的心理動機。
- 公司內部決策、預算或合約推測。
- 重複的來源限制標籤。
- 為填空而寫的空泛勵志句。

## 3. 每章內容結構

第 2–12 章原則上採用三層結構。不是要求每章顯示三個制式標籤，而是要求內容功能完整。

### A. 故事層

用 2–4 個手機友善短段落，讓讀者知道：

- 此時發生了什麼。
- 團隊或人物面對什麼改變／限制。
- 可公開確認的行動或結果是什麼。

### B. 理解層

把故事轉成青少年可以理解的知識，例如：

- 能力、機會、資源、環境和時機的差異。
- 正式 credit 中各角色的合作關係。
- 說法、官方公告、媒體轉述與正式判決的證據差異。
- 一首歌的權利與收入路徑。

### C. 回到讀者層

以一段短文、問題、callout 或既有互動收束，例如：

- 原本的方法不能使用時，你會先保留什麼？
- 參與最多是否等於獨自完成？
- 一次看似成功的選擇可能犧牲什麼？

不要讓每章都使用完全一樣的卡片和標題，避免模板感。

## 4. 分章擴寫需求

### 第 1 章 Hero

- 移除 `.hero__note` 可見提示。
- Hero 不需要大幅增加文字；維持快速建立問題和兩條路線。
- 最多只微調 lede，不要讓首屏變成長文。
- 不改已確認的 `<h1>`。

### 第 2 章「她們是誰」

應補充：

- 2018 年以六人出道、2021 年後五人體制、2025 年改名之間的時間關係。
- 為什麼歷史事件依當時團名寫 `(G)I-DLE`，現況則寫 `i-dle`。
- 團體身分不是沒有改變的直線，但也不能用傳聞補足空白。

可沿用來源：S01、S08、S09、S16、S17、S18；必須再以 register 實際 supports 為準。

### 第 3 章「五條不同的路」

這是擴寫優先級最高的章節之一。

每位成員內容可整理為：

- 公開資料能支持的起點。
- 面對的限制或轉折。
- 可確認的行動／選擇。
- 這條路帶出的能力或成長觀察。

硬性限制：

- 不使用 Shuhua 精確練習生年限。
- 不寫未核實的 Yuqi 試鏡歌曲。
- 不把 Miyeon／BLACKPINK 傳聞當成事實。
- Soyeon 的 20–30 次試鏡只能標成媒體回顧，不可升格成第一手定論。
- 不加入家庭背景、身價或匿名爆料。
- caveat 可留在資料層或集中 archive，不要恢復每張卡反覆顯示的「資料限制」區塊。

### 第 4 章「練習生不是成功保證書」

應補充：

- 練習、被評估、被選中與正式出道不是同一件事。
- 結果會受團隊需求、概念、時機、資源與合作條件影響。
- 沒有被選中不能直接等同沒有能力。
- 避免「只要努力就一定成功」或反方向的宿命論。

既有情境互動與答案取捨不可破壞。

### 第 5 章「創作者不是成功後才出現」

應補充：

- 出道不是創作參與的起點或終點。
- 〈LATATA〉可確認的 Soyeon 創作參與。
- 演唱、作詞、作曲、編曲、舞台、視覺如何形成共同作品。
- 為什麼多人 credit 是專業合作證據，而不是削弱某位參與者的重要性。

不得寫「公司沒有歌，所以 Soyeon 只好自己寫」。

### 第 6 章「2021：團隊改變」

可大幅增加媒體識讀內容，但不能重述或判定指控：

- 「有人提出說法」不等於「事情已證實」。
- 公司回應／否認、官方離團公告、媒體轉述、正式調查或判決各自能支持到哪裡。
- 為什麼負責任的編輯會停止在公開資料的界線。
- 正文只陳述 Cube 宣布 Soojin 離團，以及團體此後以五人活動。

不得把任何一方說法寫成法院已確認的事實。

### 第 7 章「《I NEVER DIE》：像重新出道一樣」

這是擴寫優先級最高的章節之一。

應補充：

- 團體活動空窗與成員在不同地點／領域活動的公開脈絡。
- 五人回歸需要重新面對位置、聲音、舞台與團隊認同。
- Soyeon 用「像重新出道一樣」描述製作心情的來源屬性。
- 重新開始不等於把過去全部清除；可以同時保留經驗並重新決定作品方向。

既有策略 slider 保留，可讓新正文自然引導到互動。

### 第 8 章「創作室：誰在決定唱什麼」

這是擴寫優先級最高的知識章節。

應補充：

- 作詞、作曲、編曲的基礎差異。
- 共同作曲者／編曲者多時，credit 應如何閱讀。
- 正式 credit 可以確認角色，不能單靠排序推算完整工作量、權力、收入或所有內部決策。
- Soyeon 在〈TOMBOY〉、〈Nxde〉、〈Queencard〉的正式 credit。
- Minnie、Yuqi 也持續參與部分歌曲詞曲或製作的保守表述。
- `self-producing` 應解釋為多位成員持續參與部分作品，不等於所有歌曲均由成員獨立完成。

不要改變卡面為官方專輯封面；現有圖案是本站原創抽象圖形，必須保留其說明。

### 第 9 章「回歸企劃遊戲」

- 不需要把遊戲前說明加倍。
- 可增加一小段「為什麼沒有唯一滿分答案」及五項指標之間的取捨說明。
- 不改任何模型規則、選項、資源、分數、結果 profile 或教育模擬聲明。
- 遊戲仍只使用企劃點、團隊能量與週數。
- 不得產生虛構銷量、榜單、收入或薪資。
- 不得破壞 `＋`／`－`／Arrow keys 的 viewport 與 focus 穩定性。

### 第 10 章「一首歌有多少種收入」

這是擴寫優先級最高的知識章節之一。

應補充：

- 錄音版本與詞曲權利不是同一組權利。
- 串流、實體銷售、公開演出、授權使用可能走不同路徑。
- 平台支付、權利人、唱片公司、發行商、出版商、集管組織及個別合約的角色差異，只能做一般機制說明。
- 為什麼「播放次數 × 固定單價 = 某位成員收入」是錯誤公式。
- 公開市場數據不能直接換算成 i-dle 或任何成員的真實所得。

禁止估算任何成員薪資、身價、分潤、續約金或真實收入。

### 第 11 章「2024 續約，2025 改名」

應補充：

- 全員續約是在 2024 年底宣布。
- 2025 年 5 月 2 日改名為小寫 `i-dle`。
- 續約與改名是兩個不同事件，不要混成同一天或同一決策。
- 改變名稱可能同時保留歷史並建立下一階段，但不得臆測未公開合約或公司內部動機。

### 第 12 章「把故事帶回自己」

可增加收束，但避免空泛勵志：

- 能力不等於立即被選中。
- 勇敢不等於完全不害怕。
- 創作與改變通常依賴合作。
- 原本方法失效時可以改變策略。
- 名稱、角色與身分可以演化。
- 回應網站核心命題：創造舞台不代表所有事情都要一個人完成。

保留目前已修正的深色文字與淺紫背景對比。

### 第 13 章「來源與可信度」

- 加入第 2.2 節的集中編輯規則。
- 可補充如何使用 S-ID、M-ID 和外部連結，但不要把本章改成冗長論文。
- 保留來源搜尋、可信度群組、全部展開／收合、圖片授權 audit、hash deep link。
- 不恢復每章的重複限制提示。

## 5. 內容資料與程式結構

### 5.1 不要把大量新增正文硬寫進 `index.html`

依 `CLAUDE.md`，事實內容與來源應集中在 `src/data/`。

建議：

- 新增 `src/data/narrative.mjs`，或擴充現有適合的資料檔。
- 以 chapter ID 組織故事、知識與反思段落。
- 每個包含可驗證敘述的內容單位要攜帶 `sourceIds`。
- 純編輯提問／反思應有清楚的資料型別或欄位，不要假裝有外部來源。

可能的資料形狀：

```js
export const CHAPTER_NARRATIVES = {
  debut: {
    story: [
      {
        text: "…",
        sourceIds: ["S01", "S07"],
      },
    ],
    explanation: [
      {
        text: "…",
        sourceIds: ["S12", "S13", "S14", "S15"],
      },
    ],
    reflection: {
      text: "…",
      editorial: true,
    },
  },
};
```

形狀可依現有程式風格調整，但必須：

- 可追蹤來源。
- 可由 content-invariant tests 驗證。
- 不把 HTML 字串混進純資料。

### 5.2 渲染元件

可在 `src/ui.mjs` 增加通用但不過度模板化的渲染器，例如：

- `renderNarrativeParagraphs()`
- `renderStoryBlock()`
- `renderReflectionPrompt()`

每個渲染單位應保留：

- 短段落。
- `data-authored-unit`。
- 合理的 `data-treatment="flat"` 或 `card`。
- S-ID 可追蹤性，但不要讓 badges 壓過正文。

不要重新顯示「閱讀限制」「資料限制」等固定標籤。

## 6. 桌面版面調整

### 6.1 目標

目前桌面版部分章節呈現「巨大標題＋一句摘要＋大量空白」。新增正文後應使用桌面空間，但不可把每一行拉得過長。

建議在 900px 或 1024px 以上，為適合的章節建立：

- 主敘事欄：約 5–7fr。
- 佐證／媒體／時間線／互動欄：約 3–5fr。
- 正文行寬仍限制在約 36–44rem。

手機維持自然單欄 DOM 閱讀順序。

### 6.2 可採用的結構

```text
章節 kicker
大標題
導言

┌────────────────────┬──────────────────┐
│ 主要故事 2–4 段     │ 圖片／關鍵事實／ │
│ 知識解釋            │ credit／互動      │
└────────────────────┴──────────────────┘

反思／收束
```

不是每章都要相同左右配置：

- 成員章可使用交錯卡片。
- 第 5 章可讓圖片與故事並列，下方接 role board。
- 第 6 章可讓媒體識讀階梯與主要說明並列。
- 第 7 章可讓故事與 slider 並列或前後錯位。
- 第 8 章可讓 credit 卡與解釋交錯。
- 第 10 章可讓權利路徑與錯誤公式形成對照。

### 6.3 留白節奏

不要全面刪除留白。調整方式：

- 第 1、7、9、12 章保留較大的轉場／舞台留白。
- 第 2、3、5、6、8、10、11 章一般桌面上下 padding 可減少約 20–30%，並以正文與模組建立密度。
- 第 13 章偏向資料庫效率，不需巨大展示留白。
- 手機 padding 不要因桌面調整而過度壓縮。

建議用 modifier／chapter selector 或 scene 內的內容密度 class，不要重新建立會和 `data-scene` 衝突的舊式視覺 class。

### 6.4 禁止事項

- 不用報紙式雙欄讓段落先讀左欄再跳右欄。
- 不讓單行正文超過舒適閱讀寬度。
- 不靠 CSS `order` 打亂 DOM 閱讀順序。
- 不把所有新增內容都放進白色陰影卡片。
- 不用超小字塞入更多內容。
